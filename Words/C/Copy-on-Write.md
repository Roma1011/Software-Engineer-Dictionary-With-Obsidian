### Copy-on-Write (COW)

**Copy-on-Write** არის ოპტიმიზაციის ხერხი: **ასლის გაკეთებისას მონაცემები მაშინვე არ კოპირდება**. ორიგინალი და ასლი ერთსა და იმავე მონაცემებს იზიარებენ, და რეალური კოპირება მხოლოდ მაშინ ხდება, როცა რომელიმე მხარე **ჩაწერას** (შეცვლას) ცდილობს.

მთავარი იდეა:

```
კითხვა  → კოპირება არ ხდება, ორივე საერთო მონაცემს კითხულობს
ჩაწერა  → ჯერ კოპირდება ის ნაწილი, რომელიც იცვლება, შემდეგ იწერება ასლში
```

**ახსნა:**
თუ ასლს უმეტესად მხოლოდ კითხულობენ, ან საერთოდ არ ცვლიან, წინასწარ კოპირება დროისა და მეხსიერების ფუჭი ხარჯია. COW ამ ხარჯს **გადადებს** იმ მომენტამდე, როცა კოპირება ნამდვილად საჭირო გახდება. თუ ეს მომენტი არასდროს დადგება, კოპირებაც არასდროს მოხდება.

```
ასლის შექმნის შემდეგ:            B-მ მეორე ნაწილი შეცვალა:

  A ──┐                            A ──► [1] [2] [3]
      ├──► [1] [2] [3]                     ▲       ▲
  B ──┘                            B ──────┘  [2'] ┘
                                   (კოპირდა მხოლოდ შეცვლილი ნაწილი)
```

#### 1. ოპერაციული სისტემა: `fork()`

ყველაზე ცნობილი მაგალითი Unix/Linux-ის `fork()`-ია (იხ. [[Fork]]). შვილი პროცესი მშობლის მთელი მეხსიერების ასლს იღებს, მაგრამ სისტემა გიგაბაიტებს არ აკოპირებს:

1. მშობლისა და შვილის მეხსიერების გვერდები **საერთოა** და ორივესთვის **მხოლოდ კითხვადად** მოინიშნება.
2. როცა რომელიმე პროცესი გვერდში ჩაწერას ცდილობს, პროცესორი შეცდომას (page fault) იწვევს.
3. ოპერაციული სისტემა ამ ერთ გვერდს აკოპირებს, ჩამწერ პროცესს ასლს აძლევს და ჩაწერას აგრძელებს.

ამის გამო `fork()` სწრაფია, მით უმეტეს, როცა მას მაშინვე `exec()` მოსდევს და შვილი მშობლის მეხსიერებას საერთოდ არ იყენებს.

#### 2. ფაილური სისტემები და snapshot-ები

ზოგი ფაილური სისტემა (Btrfs, ZFS, APFS) ცვლილებას არსებულ ბლოკზე არ წერს. ის **ახალ ბლოკში** წერს და მინიშნებას ახალ ბლოკზე გადაიტანს. ამის წყალობით **snapshot** თითქმის მყისიერად იქმნება: ის უბრალოდ ძველ ბლოკებზე მინიშნებებს ინახავს და ახალ ადგილს მხოლოდ ცვლილებების ზომით იკავებს.

იგივე პრინციპით მუშაობს SQL Server-ის **database snapshot**: ბაზის გვერდი snapshot-ში მხოლოდ მაშინ კოპირდება, როცა ორიგინალ ბაზაში ის პირველად იცვლება.

#### 3. Docker: image-ის ფენები

Docker image შედგება **მხოლოდ კითხვადი ფენებისგან** (layers). კონტეინერის გაშვებისას მათ ზემოდან ემატება ერთი თხელი **ჩაწერადი ფენა**.

```
┌──────────────────────────────┐
│  კონტეინერის ფენა (ჩაწერადი) │  ← აქ ხვდება შეცვლილი ფაილების ასლები
├──────────────────────────────┤
│  აპლიკაციის ფენა    (read-only) │
│  .NET runtime ფენა  (read-only) │  ← საერთოა ყველა კონტეინერისთვის
│  OS ფენა            (read-only) │
└──────────────────────────────┘
```

თუ კონტეინერი image-დან მოსულ ფაილს ცვლის, ფაილი ჯერ ჩაწერად ფენაში **კოპირდება** და ცვლილება ასლში ხდება. ამიტომ ერთი image-დან გაშვებული 50 კონტეინერი დისკზე image-ს 50-ჯერ არ აკოპირებს.

#### 4. C#: კოლექცია, რომელსაც ბევრი კითხულობს და იშვიათად ცვლის

კოდში COW ხშირად ასე გამოიყენება: **ყოველი ცვლილება ახალ ასლს ქმნის**, მკითხველები კი ძველ ასლს lock-ის გარეშე კითხულობენ. ეს კარგად მუშაობს, როცა კითხვა ბევრია და ჩაწერა იშვიათი (მაგალითად, კონფიგურაცია, subscriber-ების სია).

```csharp
public sealed class CopyOnWriteList<T>
{
    private volatile T[] _items = Array.Empty<T>();
    private readonly object _writeLock = new();

    // კითხვა: lock არ სჭირდება, მკითხველი ყოველთვის მთლიან, უცვლელ მასივს ხედავს
    public IReadOnlyList<T> Items => _items;

    public void Add(T item)
    {
        lock (_writeLock)                       // ერთდროულად მხოლოდ ერთი ჩამწერი
        {
            T[] copy = new T[_items.Length + 1];
            Array.Copy(_items, copy, _items.Length);
            copy[^1] = item;
            _items = copy;                      // მინიშნების შეცვლა ატომურია
        }
    }
}
```

```csharp
var handlers = new CopyOnWriteList<string>();
handlers.Add("logger");

foreach (string h in handlers.Items)   // იტერაციის დროს სხვა ნაკადი თუ Add-ს
{                                      // გამოიძახებს, ეს ციკლი არ ჩავარდება:
    Console.WriteLine(h);              // ის ძველ მასივს კითხულობს
}
```

> [!NOTE] .NET-ში უკვე ასე მუშაობს
> C#-ის **delegate**-ები და **event**-ები immutable-ია. `button.Click += handler` არსებულ სიას არ ცვლის: ის ახალ delegate-ს ქმნის, რომელშიც ძველი სია და ახალი handler-ია. ამიტომ event-ის გამოძახების დროს სხვა ნაკადის მიერ `+=`/`-=` გამოძახება უკვე მიმდინარე გამოძახებას არ აზიანებს. მზა ვარიანტი კოლექციებისთვის არის `ImmutableArray<T>` / `ImmutableList<T>` და `ImmutableInterlocked`.

> [!WARNING]
> თუ ჩაწერა ხშირია, COW **ნელდება**: `CopyOnWriteList`-ში ყოველი `Add` მთელ მასივს აკოპირებს, ანუ 10 000 ელემენტის დამატება დაახლოებით 50 მილიონ ელემენტის კოპირებას ნიშნავს. ასეთ შემთხვევაში ჯობს `ConcurrentQueue<T>`, `ConcurrentDictionary<TKey, TValue>` ან ჩვეულებრივი სია lock-ით.
